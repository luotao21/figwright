# figma-optimize

把已有设计稿的问题变成可定位、可修复、可复查的结果：**明确标准 → 读取属性与截图 → 测量 → 最小修复 → 重新验证**。
结合 `figma-codegen` 的高保真读取与 `figma-build` 的组件／token 复用，以项目规范和当前设计证据判断问题。
本技能通过 Figwright 直接检查和修复设计稿。

## 选择本次工作方式

| 用户要求                       | 行为                                                     |
| ------------------------------ | -------------------------------------------------------- |
| 检查、评审、验收、找问题       | 读取和报告，保留原稿。                                   |
| 优化、修复、调整，或检查并优化 | 在指定范围内修复有充分依据的问题，逐模块验证。           |
| 重做风格、改信息架构、改组件库 | 先明确该项设计选择与影响范围；普通优化没有包含这些授权。 |

没有目标节点时使用当前选择。选择为空且未提供可解析的目标时，请用户选中画板或提供节点链接。
范围已经明确就直接执行；只有缺失信息会改变目标、标准或修改权限时才询问。

## 1. 固定目标与标准

用 `ping` 确认插件连接，再用 `get_metadata` / `get_selection` 记录文件、页面、根节点和编辑器。
Figwright 操作的是插件已连接的文件，URL 可用于定位节点，不能让插件自动打开另一文件。
遇到多文件提示，先 `list_files`，再 `use_file({ fileName })` 固定用户指定文件；重名用 `sessionId`。
切换到库文件读取后，要重新 claim 目标文件再继续。没有明确目标时不要按文件名猜选。

从用户要求、项目设计规范、节点 annotations、既有组件 API 和变量／样式提取本次标准。
记录尺寸、主题／变量模式、语言、模块、必要状态、允许修改的对象与例外。无须为一次检查新建配置。

- 明确值、最小值和关系约束分别记录，例如“gap 必须为 16”与“gap 至少为 8”不是同一规则。
- token、组件及样式的语义优先于数值相同；同色不证明同一用途。
- 项目未规定的字体、间距或圆角属于建议，不能套用通用模板或自行设定的默认值判错。
- 无障碍按项目目标检查；未声明时明确采用 WCAG 2.2 AA 作为检查基准，并注明设计稿能验证的范围。
- 项目要求自然长高、完整组件实例等时，将其作为本次约束；不把某项目的偏好推广给所有设计。

## 2. 读取当前证据

调用 `get_design_context({ nodeId, detail: "full", dedupeComponents: true })`，不限制要检查的子树深度。
同时用 `get_screenshot({ nodeIds: [nodeId] })` 获取当前呈现；属性和截图各自承担不同证据职责。
按需读取 `get_variable_defs`、`get_styles`、`get_component_api` 和 `get_annotations`，确认实际规范来源。

- `sectionPlan`、降级 detail、`truncated` 或 `deduped` 表示证据不完整。按 section / 实例 ID 补读；
  小范围需要每个实例的内部差异时可用 `dedupeComponents: false`，不要反复请求整页。
- 用 `get_node` 精读将修改的节点及必要祖先：保留父子关系、styleIds、boundVariables、
  mainComponent、componentProperties、混合文字 `segments` 和全部布局维度。
- 去重实例的 `textOverrides` / `propertyOverrides` 是线索，不能证明每个实例的内部几何都通过。
  抽样检查只能给抽样结论。大稿维护已读／待读模块清单。
- 原始节点 `x/y` 在父级坐标系中。跨父级、旋转或缩放对象需确认可用变换；缺少变换证据时不报精确距离。
- 截图不能证明变量绑定、组件来源、真实点击区域或 Auto Layout。比例不明时不从截图报告精确 px。

连接失败或 `pluginSkewNotice` 出现时，说明具体证据缺口；受影响结果保持“待核实”。
只读检查可继续整理已有材料；写入结果未经可靠回读不得声称已修复。
Dev Mode 的写入和 FigJam 缺失的组件／变量／样式能力，按编辑器实际支持处理，不反复调用不支持的工具。

## 3. 检查并排序

读取 [references/checks.md](references/checks.md) 的适用部分。交付验收覆盖目标范围内所有适用类别；
局部问题按其相关规则检查。先在代表模块校准标准和测量方法，再检查其它模块及实例的实际例外。

1. **排版与内容**：角色字号、字体、混合文字、行高、数字对齐、标签与正式文案。
2. **布局与几何**：组内 gap、容器 inset、对齐、点击目标、嵌套圆角、裁剪、换行与页面边界。
3. **颜色与状态**：有效模式、实际背景合成、对比度、选择／错误／禁用／焦点与必要业务状态。
4. **组件与视觉层次**：实例和绑定完整，主操作易找，阅读顺序清楚，同职责元素保持一致。

优先处理阻碍阅读或主要操作的问题，其次处理确定的规范偏差。视觉层次和密度判断需说明具体影响，
不能以“更高级”“更统一”代替依据。没有规范依据的审美调整单列为建议。
相同根因合并，保留代表节点和受影响范围；不同语言、主题或实例覆盖差异不能合并掉。

## 4. 最小修复并闭环

用户要求优化时，读取 [references/repair.md](references/repair.md)，按已有授权直接修复。
每次只处理一个模块或同一根因的小批次，保留修改前属性和截图，然后回读节点、相关祖先、兄弟及实例。
重新截图，检查原问题消失且换行、布局、绑定、变体和其它必要状态没有回退。

保留内容、资产、业务状态、组件来源和主题语义。优先调整负责布局的容器／绑定／公开实例属性，
不要用拆实例、删除内容、缩小文字或隐藏溢出来制造通过。
共享变量、样式或主组件的修改会影响范围外对象，需任务明确包含该范围；否则报告库级依赖并继续独立修复。
允许范围内的选择无需重复请求批准；新增设计方向或超出范围的变更才需要澄清。

工具返回 `ok: true` 只证明调用返回。超时、部分失败或 batch 回滚错误后先读取当前状态，
不要盲目重试或假定已全部恢复。某模块两次修复仍出现同一症状时，停止该模块的写入，重新确认根因，
说明未解决项；其它独立模块可继续。

## 5. 交付可复查结果

先给结论和已解决的主要问题，再给问题表；详单可保存为用户需要的交付文件。

| 字段       | 必须包含                                                         |
| ---------- | ---------------------------------------------------------------- |
| 规则与位置 | 稳定 rule ID、节点 ID／路径／链接；截图证据则写区域。            |
| 影响与状态 | 用户受到的具体影响；通过／不通过／待核实／实现阶段待测／不适用。 |
| 实际与预期 | 实测属性、数值与单位；预期值／关系及规范依据。                   |
| 修复与复查 | 具体最小修正；修改后的值和截图／回读结果，或未修复原因。         |

示例：`layout-gap`，节点 `12:34`（表单 / 操作组），原 `itemSpacing=6`，项目要求 `spacing/action=16`；
优化后保持 `HORIZONTAL` 并绑定该变量，回读 `itemSpacing=16`、绑定 ID 正确，新截图无挤压。
这只证明该节点在所查状态满足该规则，不能推成所有按钮或所有状态通过。

报告覆盖的模块、尺寸、主题、语言、状态及抽样范围。关键数据缺失记“待核实”；
真实 DOM、ARIA、键盘可达性、焦点陷阱、字体加载与运行时响应式记“实现阶段待测”。
有未核实项时只说“已验证项通过”，不要说“全部通过”。规则通过与业务正确、整体视觉质量分别判断。

常用请求：`用 $figma-optimize 检查当前画板，只给问题。` 或
`用 $figma-optimize 检查并优化这个节点，保留组件实例和已有变量，只修改这个画板。`
